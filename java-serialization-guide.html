01

What & Why

A Java object in memory is a scattered structure — a type header, field slots, pointers to other objects on the heap. That shape is JVM-specific and can't be copied straight onto disk or across a network wire. A byte stream is the opposite: a flat, linear sequence of bytes that any file system, socket, or cache understands natively.

Serialization is the act of flattening an object graph into that byte stream. Deserialization reverses it — rebuilding a live object from the stream, restoring fields and re-wiring references.

Key distinction

Converting to bytes is mandatory for any persistence or transmission — that part isn't unique to Java. What's specific to Serializable is the exact byte format: class metadata, field names/types, and object-graph structure, all encoded in a way ObjectInputStream knows how to reverse.

02

The Stream Pipeline

Serialization always uses two stream classes stacked together — a low-level transport stream, and a high-level object-conversion stream wrapped around it.

FileOutputStream

  • Low-level — writes raw bytes to disk
  • No concept of "objects"
  • Just a pipe from program → file

ObjectOutputStream

  • High-level — converts an object into bytes
  • Cannot write to disk on its own
  • Needs an underlying stream to hand bytes to
FileOutputStream fos = new FileOutputStream("employee.ser"); // knows disk I/O
ObjectOutputStream oos = new ObjectOutputStream(fos);          // knows object → bytes
oos.writeObject(emp);

This is Java's I/O decorator pattern — ObjectOutputStream doesn't care where bytes end up, only that it's handed some OutputStream. Swap the file stream for a socket stream or a ByteArrayOutputStream and the exact same serialization logic now targets a network or memory buffer instead.

Write / Read Lifecycle

Tracing exactly what happens, and when — construction time vs. call time.

Write side

01
new FileOutputStream()
Opens the file. Nothing written yet.
02
new ObjectOutputStream()
Writes the stream header (magic number + version) immediately.
03
writeObject(emp)
Class metadata + field values are serialized and pushed to disk.

Read side

01
new FileInputStream()
Opens the file for reading. No content read yet.
02
new ObjectInputStream()
Reads & validates the stream header. Bad header → StreamCorruptedException here.
03
readObject()
Reads metadata + fields, reconstructs the object, returns it.
Constructors don't run

Deserialization allocates the object directly and populates fields from the stream — your class's normal constructors are never called. Any logging or validation inside a constructor is silently skipped. (Externalizable is the one exception — see §10.)

04

serialVersionUID

A fingerprint of a class's shape, used to check compatibility between the class that wrote the data and the class trying to read it back. 

private static final long serialVersionUID = 1L;

Every part of this declaration is load-bearing — get any piece wrong and Java silently ignores your field and falls back to auto-generation:

PieceRequirement
NameExactly serialVersionUID, case-sensitive
Typelong
static / finalBoth required (by contract / convention)
privateRecommended — each class owns its own UID

If you don't declare it

Java auto-generates one via SHA-1 over the class name, fields, methods, and interfaces — then any structural change (even adding one harmless field) produces a different auto-generated UID.

Failure mode

Serialize with UID A → modify the class → Java now auto-generates UID B → deserializing the old file throws InvalidClassException: local class incompatible — even though the change was harmless.

Once declared, treat it as stable

ChangeBump the UID?
Added a new fieldNo
Added a new methodNo
Changed a field's type incompatiblyYes
Intentionally invalidating old dataYes

It's scoped per class — Employee and Product can both happily declare 1L; the class name travels with the UID in the stream, so there's never cross-class confusion.

05

transient

Marks a field to be skipped entirely during serialization.

class Employee implements Serializable {
    private String name;
    private transient String password; // never written to the stream
}

On deserialization, a transient field comes back at its default value — null for objects, 0/false for primitives. Typical uses: passwords/tokens, non-serializable types like Thread or Socket, or derived data you'd rather just recompute.

06

Static Fields

Never serialized — they belong to the class, not the instance, so serialization (which only captures instance state) never touches them. 

class Parent implements Serializable {
    static String staticField = "Original";
}
// serialize a Child instance, then change Parent.staticField...
// deserializing later reflects whatever the CURRENT static value is,
// not the value at serialization time.
07

Custom Hooks

Override the default read/write behavior without abandoning Serializable entirely — these private methods are picked up automatically via reflection.

private void writeObject(ObjectOutputStream out) throws IOException {
    out.defaultWriteObject();  // normal serialization first
    // then custom logic — e.g. encrypt a field
}

private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
    in.defaultReadObject();    // normal deserialization first
    // then custom logic — e.g. decrypt a field
}
08

Object Graphs

Any referenced object must also be Serializable, or serialization fails with NotSerializableException.

class Address implements Serializable { String city; }

class Employee implements Serializable {
    String name;
    Address address; // must be Serializable too
}

Shared references inside the graph are preserved — if two fields point to the same nested object, deserialization rebuilds one shared instance, not two separate copies.

09

Inheritance Rules

If a superclass is not Serializable but the subclass is:

class Parent {                    // NOT Serializable
    int parentField = 10;
    Parent() { System.out.println("Parent constructor ran"); }
}
class Child extends Parent implements Serializable {
    int childField = 20;
}
What actually happens

Subclass fields are serialized normally. The superclass's fields are not — instead, the superclass's no-arg constructor runs during deserialization to initialize it. No no-arg constructor on the superclass → runtime failure.

10

Externalizable

Full manual control — you write and read every field yourself.

class Employee implements Externalizable {
    private String name;
    private int age;

    public Employee() {}  // REQUIRED no-arg constructor

    public void writeExternal(ObjectOutput out) throws IOException {
        out.writeUTF(name);
        out.writeInt(age);
    }
    public void readExternal(ObjectInput in) throws IOException {
        name = in.readUTF();
        age = in.readInt();  // must match write order exactly
    }
}

Serializable

  • Automatic, reflection-based
  • No-arg constructor not required
  • Slower, larger output (field metadata)

Externalizable

  • Fully manual read/write
  • Public no-arg constructor required
  • Faster, smaller, exact byte control

Note the one exception to §03's rule: for Externalizable, the no-arg constructor is called before readExternal() populates the fields.

11

readResolve()

Swaps the freshly deserialized object for another instance — the standard way to keep a Singleton a singleton across deserialization.

public class Singleton implements Serializable {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }

    protected Object readResolve() {
        return INSTANCE; // discard the newly built copy
    }
}

Without it, deserialization bypasses constructors and builds a second, separate "singleton" instance — breaking the identity guarantee (deserialized == getInstance() would be false).

Exceptions

ExceptionTrigger
NotSerializableExceptionA field's type doesn't implement Serializable
InvalidClassExceptionserialVersionUID mismatch between stream and class
ClassNotFoundExceptionClass of the serialized object isn't on the classpath
StreamCorruptedExceptionThe stream header / byte format is malformed

Always use try-with-resources — an exception mid-write can leave a corrupt, unusable file behind if streams aren't closed cleanly.

try (ObjectOutputStream out = new ObjectOutputStream(new FileOutputStream("data.ser"))) {
    out.writeObject(myObject);
} catch (IOException e) {
    e.printStackTrace();
}
13

Limitations

Why native Java serialization is rarely the production choice today:

IssueDetail
SecurityDeserializing untrusted data is a known remote-code-execution vector
Not cross-languageByte format is Java-specific — unreadable by Python, Go, etc.
Fragile versioningSchema evolution requires careful UID management
Verbose outputClass metadata bloats the byte stream vs. a tighter format

Common production alternatives: JSON (Jackson/Gson), Protocol Buffers, Avro, Kryo.
