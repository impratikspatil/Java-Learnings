§0Foundations

Stack vs. Heap, at a glance

Every other question in this chapter is a variation on this one picture.

The variable p is a reference sitting on the stack; the object it points to — and everything inside it — lives on the heap.
Stack — one per thread. Holds method call frames: locals, parameters, return address. Grows/shrinks automatically, LIFO. No garbage collector involved. Too deep → StackOverflowError.
Heap — one per JVM, shared by all threads. Every new lands here. Managed entirely by the Garbage Collector. Full → OutOfMemoryError.
Q130Object Lifecycle

What happens when you write new

Five steps, every time — but the JVM makes step 2 nearly free with a trick called TLAB.

Person p = new Person("Alice", 30);

Why step 2 is nearly free

Each thread owns a private slice of Eden called a TLAB (Thread-Local Allocation Buffer). Allocating inside it needs no lock — it's just bumping a pointer forward, since no other thread can touch that slice. Only when the TLAB fills up does the JVM grab a fresh one or fall back to synchronized allocation.

Interview trap: "Is new always slow?" — No. TLAB allocation is typically as cheap as stack allocation. Very large objects (big arrays) can skip Young Gen entirely and go straight to Old Gen — this is large object allocation, and it defeats the "objects die young" assumption GC tuning normally relies on.
Q126Strings & References

How strings are represented in memory

A String is a heap object wrapping a byte array — plus a pooling trick that saves memory.

String a = "cat";        // literal → String Pool
String b = "cat";        // same pool reference
String c = new String("cat"); // forces a new heap object

a == b   // true  — same object
a == c   // false — different objects
a.equals(c) // true — same content

Internal representation

FieldPurpose
byte[] valueThe actual character data (was char[] before Java 9)
byte coderFlags whether bytes are LATIN1 (1 byte/char) or UTF16 (2 bytes/char)
int hashCached hashcode — computed once, safe to cache because Strings are immutable

Why it matters

Compact Strings (Java 9+): if a string is pure Latin-1 (basically ASCII), it's stored at 1 byte/char instead of 2 — roughly halving memory for the huge majority of real-world text.

Immutability enables pooling: since a String can never be mutated after construction, it's safe for many variables to silently share the same object — nobody can corrupt it for anyone else. This is also why Strings are safe HashMap keys (hashcode never changes) and inherently thread-safe (no write ever happens, so concurrent reads never race).

Pool location: lived in PermGen before Java 7; moved into the regular heap in Java 7+, which is bigger and resizable — removing a common OutOfMemoryError: PermGen space cause from over-interning.

Strong, Soft, Weak & Phantom references

Four levels of "how eagerly can the GC take this away from me."

TypeCollected when?.get() behaviorReal use case
StrongNever, while reachableAlways returns objectNormal everyday code

WeakNext GC cycle, no strong refsObject or nullWeakHashMap, listener leak prevention
PhantomAfter finalization, pre-reclaimAlways nullPost-GC cleanup hooks (Cleaner)
// Soft — cache that survives until memory is genuinely tight
SoftReference<byte[]> cache = new SoftReference<>(loadBigData());

// Weak — entry vanishes automatically once key has no strong refs
WeakHashMap<Key, Value> sessionMap = new WeakHashMap<>();

// Phantom — pure "it's really gone now" notification, feeds Cleaner
ReferenceQueue<Resource> queue = new ReferenceQueue<>();
PhantomReference<Resource> ref = new PhantomReference<>(resource, queue);
Why Phantom matters today: it's the exact mechanism java.lang.ref.Cleaner is built on. Since .get() is always null, there's no way to accidentally re-establish a strong reference — resurrection (see Q127) is structurally impossible.
Q127Object Lifecycle

Resurrection & the death of finalize()

Yes, an object can come back from the dead — exactly once. Here's why nobody should rely on it.

The resurrection trick

class Resource {
    static Resource resurrected;

    @Override
    protected void finalize() throws Throwable {
        resurrected = this;  // self-assign to a GC root → reachable again
    }
}

When an object becomes unreachable, the JVM calls finalize() once before reclaiming it. If, inside that call, the object assigns itself to something GC considers a root (like a static field), it becomes reachable again. But the JVM tracks that finalize() already ran — so the second time it becomes garbage, it's collected silently, no second chance.

Only classes that override it get enrolled

Every class inherits an empty finalize() from Object. If your class doesn't override it with real logic, the JVM detects this at class-load time and skips the entire finalization mechanism for that class — the object is collected in one normal pass, no queue, no extra thread, no delay. Only classes that meaningfully override it get the special (slow) treatment below.

How it actually runs, step by step

  1. Object constructed → wrapped in an internal Finalizer reference, registered on an internal queue.
  2. GC finds it unreachable → instead of reclaiming immediately, moves it to a finalization queue.
  3. A dedicated, low-priority background Finalizer thread pulls it off the queue and calls finalize() — timing entirely unpredictable.
  4. Only after that completes (and no resurrection happened) is the object actually reclaimed, usually in a subsequent GC cycle.

Why it was ever used — and why not anymore

finalize() was meant as a safety net for OS-level resources GC itself can't see — file descriptors, sockets, native/off-heap memory, DB connections. GC only reclaims Java heap memory; it has zero visibility into what the OS is holding open on your process's behalf.

The problem: GC's own trigger time is already unpredictable (memory-pressure driven, not scheduled), and on top of that, the Finalizer thread adds a second, independent layer of unpredictable delay. A file or connection might stay open far longer than intended — and if the JVM shuts down abruptly, finalize() might never run at all.

Status: Deprecated since Java 9. Marked forRemoval = true since Java 18 — meaning a future JDK is expected to delete it entirely, not just discourage it. Code relying on it today is building on borrowed time.

What replaced it

try-with-resourcesFully deterministic — runs at an exact linePrimary, everyday resource cleanup
java.lang.ref.Cleaner (Java 9+)Still GC-tied, but built on PhantomReference — no resurrection riskRare safety-net cleanup if close() was forgotten

try-with-resources

Not a keyword — a pattern: parentheses right after try. Introduced in Java 7.

try (Connection conn = dataSource.getConnection();
     PreparedStatement stmt = conn.prepareStatement(sql);
     ResultSet rs = stmt.executeQuery()) {

    while (rs.next()) { /* process row */ }

} catch (SQLException e) {
    // handle it
}
// rs, stmt, conn all closed automatically — in reverse order
The exact rule: close() is called for every resource that was successfully constructed — regardless of what happens afterward (exception, return, normal exit). If construction itself throws, that particular resource never existed, so there's nothing to close.

Where it shows up in real code

File I/OBufferedReader, FileInputStream
DatabasesConnection, PreparedStatement, ResultSet — the most common real-world use
NetworkingSocket, stream wrappers around it
StreamsFiles.lines(...)
Custom typesAnything implementing AutoCloseable yourself

Any class implementing AutoCloseable (or the older Closeable) can go inside the parentheses — JDK classes already implement it; for your own classes, you implement it and define what close() does.

Know which default your production JVM actually runs — many banks still run Java 8.

VersionDefault collectorPhilosophy

Java 9 – 17G1 GCBalance pause time + throughput

Interview trap: "CMS is still available, right?" — No. Deprecated Java 9, removed entirely in Java 14. It never compacted memory, causing fragmentation; G1 replaced it by doing everything CMS did, plus compaction.
Q131Garbage Collectors

The collectors themselves

Same underlying job — reclaim unreachable objects — with very different tradeoffs on pause time vs. throughput.

Serial GC

Single thread, full stop-the-world. Simplest possible collector — no coordination overhead. Fits small heaps / single-CPU machines where long pauses don't hurt anyone.

Parallel GC (Throughput Collector)

Multiple threads do the same stop-the-world work faster than Serial, but application is still fully frozen throughout. Optimized to minimize the percentage of total time spent in GC, not any single pause. Fits batch jobs, overnight settlement runs.

CMS (Concurrent Mark-Sweep) — removed in Java 14

First mainstream low-pause collector: marked concurrently with the app, pausing only briefly. Fatal flaw: never compacted, so fragmentation built up over time, occasionally forcing the worst possible pause — a full stop-the-world compaction, often when memory was already tight.

G1 GC (Garbage-First)

Splits the heap into ~2000 equal-sized regions, any of which can play Eden/Survivor/Old dynamically. Prioritizes collecting regions with the most reclaimable garbage first, and does compact — no CMS-style fragmentation. You can set a target: -XX:MaxGCPauseMillis=200.

ZGC & Shenandoah

Sub-millisecond pauses regardless of heap size (tested to multi-terabyte heaps), by doing almost all marking/relocating/reference-updating concurrently with the app. ZGC uses colored pointers + load barriers; Shenandoah uses Brooks pointers. Built for real-time trading engines and strict-SLA systems.

Decision framework: small heap / simplicity → Serial · maximize total throughput → Parallel · balanced general purpose → G1 (default) · ultra-low latency, huge heap → ZGC or Shenandoah.
Q134Memory Areas

All the areas of JVM memory

Not just "heap and stack" — the complete map splits into shared vs. per-thread regions.

The trap most people fall into: stopping at "Heap and Stack." The real conceptual split is shared vs. per-thread, and only Heap (+ Metaspace, via class unloading) is touched by garbage collection — Stack, PC Register, and Native Method Stack are managed automatically by call/return mechanics, with zero GC involvement.

Q136Leaks & Monitoring

Memory leaks — with a garbage collector?

GC only reclaims what's unreachable. A Java "leak" is really an accidental, lingering reference.

Common real causes

CauseWhy it leaks
Static collectionsstatic fields are GC roots — live for the app's entire lifetime; items added but never removed grow forever
Unclosed resourcesConnection pool exhausts even though heap looks fine
Listeners never unregisteredRegistry keeps the whole object graph alive long after it's logically done
Non-static inner classesImplicitly hold a hidden reference to the enclosing instance — keeps it alive if the inner object outlives it
ThreadLocal not removedPooled threads never die — value stays attached forever unless .remove() is called
// Non-static inner class leak
class OuterService {
    private byte[] bigData = new byte[100_000_000];
    class InnerTask implements Runnable {   // implicit ref to OuterService.this
        public void run() { /* work */ }
    }
    Runnable getTask() { return new InnerTask(); }  // leaks bigData if handed off long-term
}

// ThreadLocal leak in a pooled-thread server
threadLocal.set(new ExpensiveObject());
// ... forgot: threadLocal.remove();

Prevention map

Static growing collectionsEviction/expiry logic, or bounded caches (Caffeine, Guava)
Unclosed resourcesAlways try-with-resources
Listener leaksWeak-referenced listener lists, explicit unregister in lifecycle hooks
Inner class refsPrefer static nested classes unless outer instance is truly needed
ThreadLocalAlways .remove() in a finally block
How to actually find one in production: take a heap dump (-XX:+HeapDumpOnOutOfMemoryError), load it in Eclipse MAT, run the Leak Suspects report / dominator tree to find unexpectedly large retained-size objects, then trace the GC root path back to find what's holding the reference.
Q137Memory Areas

Metaspace vs. PermGen

PermGen (pre-Java 8)Metaspace (Java 8+)
LocationFixed heap-adjacent regionNative (off-heap) memory
SizingFixed max (-XX:MaxPermSize), often smallGrows dynamically, uncapped by default
Common failureOutOfMemoryError: PermGen space from heavy class generationUnbounded native memory growth if a ClassLoader leak exists

One line: Metaspace replaced PermGen by moving class metadata to dynamically-resizable native memory, eliminating the classic PermGen OOM — at the cost of a new, harder-to-spot native memory growth risk if left uncapped.

Q139Leaks & Monitoring

Is heap size fixed?

No — configurable and elastic between -Xms (initial) and -Xmx (max). The OS grants the JVM process virtual memory up to -Xmx; the JVM then internally divides that space among Eden/Survivor/Old Gen.

Production tuning note: many teams set -Xms equal to -Xmx specifically to avoid runtime heap resizing, which itself causes extra pause time — trading a bit of "wasted" memory at startup for consistent, predictable GC pause behavior. Matters a lot where latency predictability is critical (e.g. trading systems).

[GC [ParNew: 1800K->90K(1800K), 0.0552314 secs] 22320K->20610K(65536K), 0.0553213 secs]
[Times: user=0.04 sys=0.01, real=0.06 secs]
CollectorParNew — parallel, stop-the-world, young-gen-only (historically paired with CMS)
Young gen freed1800K → 90K = 1710K reclaimed
Total heap change22320K → 20610K = 1710K reclaimed (matches — old gen untouched this cycle)

Q141Reading GC Logs

Reading a G1 mixed-pause log

[GC pause (G1 Evacuation Pause) (mixed) 2048M->1024M(4096M), 0.1200000 secs]
[GC pause (G1 Evacuation Pause) (mixed) 1024M->512M(4096M), 0.1100000 secs]

"Mixed" means G1 collected young regions plus a subset of old-gen regions with the most reclaimable garbage — its mechanism for avoiding old-style full-heap stop-the-world pauses.

Reading it: 2048M → 1024M = 1024M freed, out of 4096M total capacity, in a 120ms pause; second line frees another 512M in 110ms.

Three levers to reduce these pauses

-XX:MaxGCPauseMillis=<N>Lower it → G1 does more, smaller cycles instead of fewer, bigger ones
-XX:InitiatingHeapOccupancyPercentLower it (default 45%) → mixed GCs start earlier, with less accumulated garbage per cycle
-XX:G1HeapRegionSizeSmaller regions (power of 2: 4M/8M/16M/32M) → more granular, shorter pause increments
